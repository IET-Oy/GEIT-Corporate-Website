A. Current implementation and architecture

  • Frontend: Existing React, TypeScript, Vite and Tailwind corporate website, with Wouter routing, TanStack Query and Recharts. No new application or Next.js rewrite. The corporate site and approved navigation are preserved.
  • Application entry: /energy-saas redirects to /app. The authenticated shell selects an organisation, checks the current session and presents module links. Signed-out users see an authentication gate, not customer records.
  • Account routes: /app/sign-in, /app/register, /app/forgot-password, /app/auth/callback, /app/reset-password.
  • Workspace routes: /app, /app/organisation-settings, /app/energy-management, /app/energy-consulting, /app/energy-auditing, /app/renewable-energy, /app/battery-flexibility, /app/carbon-footprint, /app/digital-energy. /app/projects-reports is explicitly planned, not an operational report hub.
  • Backend: Express 5/TypeScript, compiled with esbuild. Same-origin API under /api; session/auth/organisation endpoints under /api/platform; energy APIs under /api/platform/energy/:orgId; six engineering/sustainability modules under /api/platform/engineering/:orgId/:module.
  • Persistence: Existing external Supabase PostgreSQL, Auth and private Storage. Request handlers use the authenticated user's JWT and publishable key, not an owner/service-role key. The privileged DB connection is used for migrations and inspection. The API also eagerly imports an existing, separate legacy corporate-enquiries database dependency through @workspace/db; deployment must account for both.
  • Existing additional modules: Persistent consulting, efficiency/auditing, renewable, battery, carbon and digital-twin projects/scenarios use validated inputs and saved calculation snapshots. Public descriptions of services are not separate SaaS engines.

Primary evidence: src/platform/app-routes.tsx, src/config/platform-modules.ts, src/platform/workspace.tsx in the website; API src/routes/{platform,energy,engineering}.ts; package manifests; artifact service configuration.

C. Database, authentication and authorisation

Persistent database connection: verified. The current read-only metadata audit connected using certificate-verified TLS and reported:

  • 6 repository migration checksums match the applied ledger.
  • 15 tenant tables have Row Level Security enabled.
  • 0 anonymous/PUBLIC grants on GEIT public-schema tables.
  • 16 security-definer functions have a restricted search path.
  • Document bucket is private, with a 10,485,760-byte limit.

Schema covers profiles, organisations, memberships, audit events, eight energy tables, engineering projects/scenarios and versioned emission factors. Policy/RPC source binds records to organisation membership, constrains role-controlled writes, preserves the final owner and restricts document keys by organisation. Composite foreign keys, interval exclusions and atomic RPCs protect tenant links/import commits. RLS checks inspect metadata; they do not prove every policy's behavioural correctness.

Authentication: Actual Supabase password auth, verified-email requirement, token refresh, sign-out, registration and PKCE recovery/callback implementation. Tokens and PKCE verifier use HttpOnly cookies rather than browser local/session storage. Mutations enforce exact origin and a custom request header. Roles are owner, administrator, energy manager, consultant, analyst and reader; permissions differ by operation.

Freshly verified: unauthenticated energy and engineering requests return 401; signed-out session returns no identity or organisations. PKCE cookie and transient provider failure regressions pass. These controlled tests are not a real-inbox account activation or password-recovery test.

Not freshly verified: successful customer login, cross-organisation positive/negative record access, direct REST/RPC bypass, role mutation permissions, storage upload/download isolation and writes surviving reload. The existing live harness creates/deletes synthetic accounts and records; it was deliberately not run against this unconfirmed database target. Metadata flags alone cannot establish complete tenant isolation.

Evidence: scripts/audit-database.mjs, migrations/001–006, src/lib/platform-session.ts, src/lib/private-storage.ts, API route guards. Historical live evidence is separately recorded in the 18 October audit; it is not counted as a new test result.

D. Calculations and data quality

  • Units: Wh/kWh/MWh/MJ/GJ normalise to kWh; W/kW/MW mean interval-average power multiplied by elapsed hours. Cumulative meter registers and instantaneous power samples are not accepted as interval energy.
  • Time: Explicit UTC offset required; supported years 2000–2100; positive intervals up to 24 hours. UTC durations determine energy; IANA site zones determine local grouping, including DST. UI date inputs use browser-local time.
  • Missing data: Gaps are not filled or silently treated as measured zero. Only full intervals inside the requested window are analysed; coverage and caveats are returned. Twin incomplete hourly buckets remain null.
  • Validation: Non-negative finite bounded values, exact import headers, no spreadsheet formula cells, malformed/duplicate/overlapping rows rejected. Imports allow 1–5,000 rows, 2 MiB files; XLSX expansion is bounded to 16 MiB and 200 ZIP entries. Analysis is bounded to 10,000 intervals and 366 days.
  • Energy KPIs/cost: Sum normalised energy; power = energy/elapsed hours; peak is the highest interval average. Observed average and load factor use measured hours. Flat-rate cost includes energy, observed local-day standing charges and observed monthly peaks, not a complete utility invoice. No tax/TOU/tier modelling or missing-data extrapolation.
  • Solar and storage: Documented baseline yield and AC energy-balance dispatch; capacity/SOC/power and one-way efficiency constraints. No claim of advanced optimisation or measured battery performance.
  • Forecast: At least 35 complete consecutive days; mean of previous four same-hour-of-week observations, held-out weekly MAE/RMSE/WAPE and empirical error bands. Robust median/MAD anomaly screening is not fault diagnosis.
  • Carbon: Source, geography, units and validity/version metadata; frozen factor snapshots; supported Scope 1/2 and limited supported Scope 3 inputs. A complete assured inventory is not established.
  • Provenance: Saved input/source snapshots, versioned engines and server HMAC verification before trusted display/export. Direct authenticated RPC access does not make arbitrary submitted results authentic. Unsigned or changed historical outputs fail closed and must not be silently re-certified.

No measurements were invented or imported during this audit. Synthetic test examples are not customer operating data. See docs/geit-energy-management.md, docs/engineering-modules.md and docs/carbon-digital-modules.md for assumptions and supported workflows.

F. Security, deployment and integration gaps

  • Process-local limits: Auth 20 writes/minute/IP, other platform writes 60/minute/IP, AI an additional 5/account/minute. In-memory counters reset on restart and do not span replicas. A shared/edge limiter is required before public scaling; proxy IP trust needs real-gateway validation.
  • Origin/canonical setup: Production-context configuration inspection found PLATFORM_ORIGIN and VITE_PUBLIC_SITE_URL absent. Production API intentionally refuses startup without a valid explicit HTTPS origin. The local smoke supplies a controlled origin; it does not establish production configuration.
  • Secrets present by existence only: SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, SUPABASE_DB_URL, SESSION_SECRET. Managed DATABASE_URL also exists. Values were not exposed in this report. Privileged DB URLs belong only in secure server/migration configuration.
  • Signing-key continuity: Preserve the signing key across instances and restores; unplanned rotation invalidates old report authentication. Versioned key rotation/recovery is not demonstrated.
  • Email: Supabase Auth delivery, redirect allowlists, same-browser verification/recovery and intended-domain cookies need a real-inbox test. Adding an existing verified user to an organisation is implemented; invitation email delivery is not.
  • Storage: Private bucket/policy infrastructure exists; no complete customer-facing document library or file-intake/malware-scanning workflow. Privacy, retention and deletion obligations need operational review.
  • Backups: Retention/PITR settings, separate storage-byte backups, RPO/RTO and an isolated restore drill were not available for verification. Database metadata success does not prove recoverability.
  • External measurements: No configured live meter/IoT, weather, grid or market-data connector. Real-time operation would need suitable equipment/protocol access, provider credentials, licensing and operational monitoring.
  • AI: OPENAI_API_KEY, GEIT_AI_MODEL and enabled GEIT_AI_ENABLED are absent. Enable only after consent/privacy and live authorised-evidence tests. Calculations do not require AI.
  • Billing: No configured or verified payment integration/webhooks were established. Paid entitlements are not operational or claimed; provider secrets, signed webhooks and lifecycle/replay tests would be prerequisites.
  • Scale: Bounded lists, synchronous import/calculation/export processing and large frontend chunks limit scale. No load/soak test or guaranteed performance envelope. PDF tables are summaries, not full-data exports.
  • Logs/error handling: Inspected logger excludes request bodies/query strings and redacts auth/cookie fields; API errors are generic JSON. Full operational log access, retention, alert routing and independent privacy/data-flow review remain outstanding.
  • Documentation drift: Earlier foundation documentation still describes older navigation/planned-module scope. Use current source contracts and module guides; update stale foundation statements after this audit rather than interpreting them as current behaviour.

Existing artifact configuration declares a root static website with SPA rewrites, an API service routed under /api with health checks and a development-only design sandbox. Those declarations were inspected, not a live published deployment. No publishing action was taken.

Then test login → site/meter → import preview/commit → analysis/chart update → reload → export in a browser. Do not run the mutating harness against customer production.

  3. P0 — Establish recovery. Confirm retention/PITR, back up object bytes and stable report-signing keys, and complete an isolated restore drill.
  4. P1 — Harden public operation. Shared rate limiting, real-gateway proxy checks, production monitoring, privacy scan remediation/re-run and independent tenant/security review.
  5. P1 — Close product-scope gaps deliberately. Decide whether a pilot needs an aggregate dashboard, equipment register, consolidated report hub or background notifications. Until built and tested, describe the current product as manual-import analysis and saved scenarios—not continuous monitoring.
  6. P1 — Enable integrations only when configured. Test measurement ingestion and optional AI against authorised records; keep unavailable integrations disabled. Add billing only with a selected configured provider and verified webhook lifecycle tests.
  7. P2 — Performance, documentation and regression coverage. Profile bounded worst-case datasets, split large bundles, add pagination/background processing when required, address the source-map diagnostic, update stale setup wording and run authenticated responsive/accessibility regression.

Recommendations only: no fixes were applied during this read-only audit.

H. Final readiness decision

INTERNAL TESTING is the evidence-supported classification. Real persistence, authenticated infrastructure and tested baseline calculations mean the system is beyond a UI prototype. Missing fresh tenant/end-to-end verification, real-inbox validation, published configuration, recovery evidence and public-scale controls prevent a pilot-ready or production-ready claim.

A limited pilot should be reconsidered only after the P0 gates pass in the intended environment and its scope explicitly excludes unfinished live monitoring, notification delivery and unconfigured integrations.
