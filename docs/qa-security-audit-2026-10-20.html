2. Fixes and regression coverage

High: remote fixture writes were insufficiently guarded — fixed

Reproduction before the fix: the integration harness rejected NODE_ENV=production, but accepted any configured remote Supabase connection when run as development. Process mode does not classify a remote database. Account creation, object upload and cleanup could therefore target an unintended environment.

The harness now fails before connecting unless the operator explicitly enables fixture writes and names an exact staging Supabase project reference matching its HTTPS endpoint. Production mode, mismatched hosts, credentials in the URL and malformed endpoints are rejected. The standalone energy-boundary harness has the same guard. Cleanup signs out only its own session, preventing accidental invalidation of a concurrent browser fixture session.

Verified: two fixture-safety tests passed; an unapproved harness invocation exited nonzero with “Fixture writes disabled” before connecting. This is a safety guard, not automated proof that an operator-labelled project is non-production.

Accessibility/validation: auth fields lacked native constraints — fixed

Browser inspection found missing required and length attributes despite existing submit-time validation. Added required email/password/name semantics, email/name/password bounds, and focus on the first invalid field for sign-in, registration, recovery and password update. Existing custom messages, ARIA error states, routes and styling remain.

Verified after fix: blank and deliberately invalid submissions focus the expected field; invalid registration shows email and minimum-password messages; no POST requests occurred. Required password bounds are 12–128 on registration/reset. A browser advisory about adding a username hint to the reset-password form remains; not a runtime failure.

New automated safety checks

  • Real local HTTP requests against Express with a synthetic provider: foreign-organisation denial, reader mutation denial, 12 concurrent own-tenant reads with tenant filters on every query, foreign report IDs, strict rejection of forged ownership fields and injection-shaped identifiers. These are server-authorization tests, not direct database RLS tests.
  • Empty and >2 MiB imports, invalid encoding, corrupt ZIP/XLSX, executable/disguised filename, missing/extra cells, unsupported units, formula-shaped and nonfinite values, row limit, BOM/quoted CSV, multi-sheet XLSX and actual compressed content expanding beyond 16 MiB.
  • 16 independent parallel parser calls preserve their own quantities and duplicate-error previews. Eight concurrent 5,000-row parser calls were additionally benchmarked.
  • Actual downloaded CSV/XLSX template headers, filled with a synthetic row, round-trip through the parser; demo template already contains data. Real CSV/XLSX/PDF export bytes are generated and checked for expected consumption, workbook structure, safe string cells and PDF signature. No persistent-record report-download claim is inferred.

The first new template test incorrectly tried to import an intentionally empty template directly; it failed and was corrected to fill synthetic data before import. The product did not require a template change. Final affected tests passed.

High-priority multi-user launch blocker: permitted year-long calculations can block unrelated requests for seconds. Move bounded work into workers/jobs or introduce a proven equivalent grouping algorithm with DST/fractional-time-zone regression tests and explicit concurrency limits. No unverified algorithm replacement was made in this audit.

  • Rate limiting is per-process, not distributed. Verify trusted proxy/IP behaviour on the actual deployment and use a shared gateway/store before multi-instance launch.
  • No dedicated heavy-work queue or measured backpressure exists for simultaneous parsing, calculation and export requests. Authentication does not itself protect a process from expensive authorised workloads.
  • List caps (250 module records, 500 factors/sources), 10,000 analysis intervals and 366-day periods bound workloads but do not constitute pagination or capacity proof.
  • No staging database EXPLAIN/lock contention/connection saturation or p95/p99 authenticated HTTP load test was run. Large uploads, event bursts and provider outages under sustained load remain unmeasured.
  • Build warnings remain: main JS about 813 kB minified, app chunk about 505 kB, WebGL about 528 kB; tooltip source-map diagnostic. These do not fail the build but need performance review on physical low-powered devices.

5. Security review and operational gaps

  • Medium SAST findings reviewed: platform-session.ts writes access/refresh tokens returned by Supabase. The sign-in flow validates provider output and verified email, uses fixed cookie names, HttpOnly, Secure on HTTPS, SameSite=Lax and scoped paths. This is not a confirmed attacker-controlled session fixation path. The scanner findings remain visible; actual published cookie/session rotation testing remains required.
  • Injection and disclosure: tested malformed/ownership inputs fail closed; parameterised database helper usage and constrained table selection inspected. JSON API errors omit internal provider details; logs serialize path without query, method and status instead of bodies/tokens. This is not exhaustive penetration testing or a complete log-retention audit.
  • Transit: database audit connected using certificate verification; Supabase endpoint is HTTPS. Production configuration rejects non-HTTPS origins. Published TLS, security headers, proxy cookies and custom domain were not verified.
  • At rest: a private bucket/RLS limits access; this does not independently establish encryption-at-rest configuration, key ownership, backup encryption or retention. Those controls require provider/operational evidence.
  • Recovery: backup/PITR settings, Storage-byte backups, restore drills and signing-key recovery remain unverified. Private Storage metadata alone is insufficient for object-byte recovery.
  • Secrets: no values were printed or embedded in the report. Required runtime/setup names are SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, SUPABASE_DB_URL, stable SESSION_SECRET, managed legacy DATABASE_URL where imported, production PLATFORM_ORIGIN and build-time VITE_PUBLIC_SITE_URL. Optional AI uses OPENAI_API_KEY, GEIT_AI_MODEL and GEIT_AI_ENABLED only after approval. No billing secret is needed while billing is disabled.
  • SEO/build configuration: VITE_PUBLIC_SITE_URL is absent during this build, so sitemap generation explicitly skipped. Set the verified public HTTPS origin rather than inventing a canonical URL. No publish action was taken.
